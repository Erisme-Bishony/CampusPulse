# CampusPulse 服务端待完成事项（以课程选题为准）

本清单依据 `Documents/安卓选题 .docx` 中「一种基于安卓的个性化校园活动推荐平台」的原始描述核对。该选题要求 Android 与服务器通过数据库交换数据；服务器实现「协同过滤 + 基于内容推荐」，管理用户信息和活动资源；数据库存储活动并支持全文检索和用户行为分析。本文只列目前仍需要服务端完成或验证的工作。

## 1. 推荐算法：补齐协同过滤与个人行为

当前 `RecommendationService` 已实现兴趣标签 Jaccard 相似度、全局报名/浏览热度、冷启动、过滤已报名/已结束活动及推荐理由，但没有协同过滤。`behavior` 表已经记录 `VIEW`、`SHARE`、`DURATION`，其中停留时长及个人浏览历史尚未用于推荐；用户的报名历史目前只用于排除已报名活动。

建议保留现有 `GET /api/v1/recommendations?limit=N` 响应结构，在服务端增加一个可解释的小规模协同过滤分数：

1. 用用户对活动的报名、浏览、停留时长生成偏好强度；报名权重大于浏览，停留时长设置上限，避免长时间挂机影响排序。
2. 比较用户的活动偏好，得到相似用户；相似用户喜欢、当前用户未报名的活动形成协同过滤候选及分数。
3. 将协同过滤分与现有标签内容分、活动热度分组合。没有足够行为或相似用户时，回退到标签与热度分。
4. 保持已报名、已结束、未发布活动的过滤，返回 `score` 和准确的 `reason`。推荐理由应能区分「兴趣匹配」「相似用户喜欢」「近期热门」。
5. 增加测试：两名标签相同但行为不同的用户获得不同排序；浏览/停留/报名影响分数；无行为冷启动；过滤与分数范围；真实 MySQL 上用演示数据验证。

课程演示规模很小，算法可以在 Java Service 中计算，无需机器学习框架。请在报告中写实际采用的公式、权重、输入数据及冷启动规则。现有接口保持兼容，Android 首页会直接展示后端返回的活动和理由。

## 2. 真正使用数据库全文检索

数据库脚本已创建 MySQL 全文索引，但 `ActivitySpecifications.publishedFilter()` 当前使用四个字段的 `LIKE` 查询。请将服务端活动关键词检索接到 MySQL `MATCH ... AGAINST`（中文关键词按已有 ngram 索引处理），验证中文标题、描述、地点检索，并明确排序规则。继续保留现有 `/api/v1/activities` 的参数和分页响应，避免影响 Android。

## 3. 用户、活动资源管理和行为分析

- 管理员用户页当前只读。增加至少一项实际用户管理操作，例如启用/停用账号，并验证停用账号不能继续使用学生接口。
- 活动已支持新建、编辑和上下架。补充删除或软删除及其与报名记录的关系；如果采用软删除，在界面和报告中说明。
- 仪表盘当前展示行为记录总数。增加可核对的浏览量、报名量、分享量与停留时长汇总，最好能按活动查看，让「分析用户行为数据」在演示中可见。
- 检查管理员页面操作后的数据库数据、权限与错误提示。

## 4. 联调接口与验收

Android 已使用以下接口：活动与标签、注册登录、用户资料与兴趣、报名、`GET /api/v1/recommendations`、`POST /api/v1/behaviors`。请保持这些响应字段兼容。Android 日历使用 `/api/v1/users/me/registrations` 的已报名记录，本地提醒使用 Android 系统能力，不要求新增提醒 API。

联调时按以下顺序验收：管理员发布活动 → Android 检索与查看 → 用户报名 → 浏览/分享/停留行为入库 → 推荐排序或理由变化 → 管理员看到对应统计。还需覆盖冷启动、满额、截止、取消报名、停用用户和数据库断连。建议留存接口测试结果与页面截图，供最终报告和答辩使用。

> 原题中的「推送给用户」目前由 Android 首页主动读取个性化推荐列表来呈现。如果教师要求系统通知式的主动推送，应单独确认触发时机和通知方案；现有本地通知用于报名提醒。
